# Live Console verification runs: DEMO RUNS, NOT RESULTS

One live conversation per run (autopilot customer script, llama3.1:8b at temperature 0 on
local Ollama), from a fresh clone (`~/skypiea-live-fresh2`, commit 17585e8 + 9c701f9 for the
predictor-killed run) on 2026-11-06. Local kind cluster on a laptop: cold starts are lower than
on AWS, both stacks share one node, and images were pre-pulled (every start is a cached start).
Baseline policy scale-to-zero, mirror mode concurrent. The LLM was loaded into memory with one
throwaway request before the first run.

Files per run: `summary.json` (the console's totals and per-call rows) and `export.csv` (the
console's CSV export; metadata only). `runs.md` holds the tables, generated by
`python -m demo.live_runs_table results/live_console_demo`.

Known measurement caveats (all disclosed in runs.md and docs/handoff/LIVE_CONSOLE_REPORT.md):

- These runs used the baseline lane that queued a baseline call only after the predictive call
  had RETURNED (fixed afterwards in c4c8e9c). In 4 calls the baseline gap was longer than the
  Skypiea gap (listed in runs.md). Each is the first use of its server in the session, cold on
  the scale-to-zero baseline regardless of the gap. The hint off/on comparison is
  Skypiea-vs-Skypiea and does not depend on the baseline lane.
- `export.csv` rows of `coding_hint_on` are in record order, not call order (fixed afterwards
  in d17b6d9); runs.md orders calls by their measured start.
- One conversation per cell, the LLM chooses its own tool order, and run-to-run variance is
  large (the same cold user_lookup took 1.9-2.9 s). Do not compute differences between runs
  as if they were effects.

`invalid_wait_for_both_mirror/` holds two discarded runs from the first mirror design. Do not
quote them.
